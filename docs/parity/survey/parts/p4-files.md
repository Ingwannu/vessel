Source root: `~/refs/paseo-latest/packages`. Short names: `msgs` = `protocol/src/messages.ts`, `dc` = `client/src/daemon-client.ts`, `wfs` = `server/src/server/session/files/workspace-files-session.ts`, `svc` = `server/src/server/file-explorer/service.ts`, `app` = `app/src`.

## Path safety, binary detection, limits (shared rules for all file RPCs)

All workspace file RPCs go through `svc` and take `cwd` (workspace root, absolute or `~...`) plus `path` (relative to cwd, or absolute inside cwd; `resolvePathFromBase` in `server/src/server/path-utils.ts`). Not a Paseo message: nothing is sandboxed beyond these rules.
- `resolveScopedPath` (svc:~540): `expandUserPath(root)` -> `resolvePathFromBase(root, rel)` -> lexical `assertWithinWorkspace` (path.relative must not be `..`, start with `..`+sep, or be absolute) -> `fs.realpath(root)` and `fs.realpath(requested)` -> second containment check on the real path. A realpath that fails with ENOENT/ENOTDIR/ELOOP returns the lexical path (so create/missing work). Error text: `Access outside of workspace is not allowed` (`ACCESS_OUTSIDE_WORKSPACE_MESSAGE`).
- Reads open with `O_RDONLY | O_NOFOLLOW` on non-Windows (`READ_FILE_OPEN_FLAGS`), so a symlink leaf is refused even if realpath said it is inside. Directory listing skips dangling symlinks and symlinks pointing outside the workspace (`isMissingEntryError`, `isOutsideWorkspaceError`) instead of failing.
- Mutations (rename/duplicate/delete) refuse the workspace root (`Cannot rename|duplicate|delete the workspace root`) and delete/lstat the requested path not the realpath (a symlink is removed, not its target).
- Names for create/rename: trimmed; rejected if empty, `.`, `..` (`Invalid name`) or containing `/` or `\` (`Name cannot contain path separators`).
- Binary/text detection (`isLikelyBinary`): any NUL byte => binary; else control bytes (<32 except TAB/LF/CR, and 127) / length > 0.3 => binary. Also binary if not valid UTF-8 (`TextDecoder fatal`). Streamed reads use the same rule over the whole file (`isFileHandleBinary`, chunked 256 KiB, `decoder.decode(stream:true)`). Metadata sniff (`sniffFileType`) reads only the first `FILE_TYPE_SAMPLE_BYTES = 8192` bytes and uses `isValidUtf8Prefix` (tolerates a multi-byte char cut at the end).
- Kind by extension first: image (`.png .jpg .jpeg .gif .webp .svg` -> `image/png|jpeg|gif|webp|svg+xml`), binary by extension (`BINARY_MIME_TYPES`: `.pdf application/pdf`, `.zip application/zip`, `.gz application/gzip`, `.mp3 audio/mpeg`, `.mp4 video/mp4`, `.woff2 font/woff2`; unknown binary => `application/octet-stream`), else text (`.json` => `application/json`, everything else `text/plain`). Note: `.svg` is classified `image`, not text.
- Constants: `FILE_EXPLORER_STREAM_CHUNK_BYTES = 256*1024`, `MAX_EDITABLE_FILE_BYTES = 1024*1024` (editor writes), `MAX_WEBSOCKET_MESSAGE_BYTES = 100*1024*1024` (`protocol/src/websocket-message-limit.ts`, close code 1009 beyond it), `MAX_RELAY_WEBSOCKET_MESSAGE_BYTES = 32*1024*1024`, app `MAX_SESSION_DOWNLOAD_BYTES = 64*1024*1024`, download token TTL `downloadTokenTtlMs ?? 60000` (`bootstrap.ts:699`), upload stale timeout 10 min.
- Revision string (`fileRevision`): `` `${dev}:${ino}:${size}:${mtimeNs}` `` from a BigInt stat. `modifiedAt` is `stats.mtime.toISOString()`. Conflict detection prefers `expectedRevision`; falls back to comparing `modifiedAt` when no revision is sent.
- Capability flags in `server_info.features` (`websocket-server.ts:2105-2174`, schema msgs:3784-3869): `workspaceFileEditing`, `fileByteWrites`, `fsEntryOps`, `fsEntryDuplicate`, `directorySync`. All `true` on 0.15.4; app hides new/rename/delete (`fsEntryOps`) and duplicate (`fsEntryDuplicate`) if missing (`app/components/file-explorer-pane.tsx:~455-461`). Client comment `COMPAT(fileReadByteBudget)`: v0.5.0 daemons enforce `maxBytes` server-side; older ones stream anyway and the client drops the data.

## Protocol: file explorer read RPC (`file_explorer_request` / `file_explorer_response`)

- Request (msgs:2833): `{type:"file_explorer_request", cwd:string, path?:string (default "."), mode:"list"|"file", requestId, acceptBinary?:boolean, maxBytes?:int>0}`.
- Response (msgs:6162): `{type:"file_explorer_response", payload:{cwd, path, mode, directory: {path, entries[]}|null, file: {...}|null, error: string|null, requestId}}`.
  - `FileExplorerEntry` (msgs:2809): `{name, path (relative, "/" separators, "." for root), kind:"file"|"directory", size:number, modifiedAt:ISO string}`. `kind` is from the dirent (symlink to a dir that is not isDirectory() reports "file"); `size`/`modifiedAt` come from `fs.stat` of the resolved target.
  - `FileExplorerFile` (msgs:2817): `{path, kind:"text"|"image"|"binary", encoding:"utf-8"|"base64"|"none", content?, mimeType?, size, modifiedAt, revision?}`. Text => utf-8 content inline; image => base64 inline; binary => `encoding:"none"`, no content.
- Server handler: `wfs.handleFileExplorerRequest` (wfs:247), dispatched from `server/src/server/session.ts:3134`. `cwd` is trimmed; empty => `error:"cwd is required"`.
  - list: `listDirectoryEntries` (svc:~125): readdir withFileTypes, per-entry stat in parallel, sorted by `modifiedAt` DESC then `name.localeCompare` (client re-sorts, see tree). Not a directory => `Requested path is not a directory`.
  - file, `maxBytes` set: `getDownloadableFileInfo` first; `size > maxBytes` => error `File is too large to display` (no data sent).
  - file, `acceptBinary && host.hasBinaryChannel()` (`onBinaryMessage !== null`, session.ts:931): `streamExplorerFile` emits binary frames (below) and the JSON response is NOT sent on success; the client synthesizes a `file_explorer_response` with `file:null,error:null` after `FileEnd` (`dc:7053-7140`) and reads bytes from `completedBinaryFileReads`. Otherwise `readExplorerFile` inline JSON (whole file in memory, base64 for images).
  - Errors: logged, response with `error: message` (`getErrorMessage`).
- Not found: no LSP / language server feature exists anywhere in the packages (grep `lsp` hits only provider tool-name mapping in `server/src/server/agent/providers/omp/tool-call-mapper.ts` tests and an OpenCode permission key `lsp` in `providers/opencode/options.ts:33`). Editor "intelligence" is CodeMirror extensions only (see Source panel).

### Binary file-transfer frames (`protocol/src/binary-frames/file-transfer.ts`)
- Opcodes `FileTransferOpcode`: `FileBegin=0x10`, `FileChunk=0x11`, `FileEnd=0x12`. Demuxed by `binary-frames/demux.ts:35` (`kind:"file_transfer"`).
- Layout: `[opcode u8][requestIdLen u8 (1..255)][requestId utf8]` then
  - Begin: `[metaLen u16 BE][metadata JSON]` (metadata <= 0xffff bytes). `FileBeginMetadataSchema = {mime:string(min 1), size:int>=0, encoding:"utf-8"|"binary", modifiedAt:string, revision?:string, fileName?:string}`.
  - Chunk: raw payload bytes (server chunk = 256 KiB; client upload default `chunkSize` 128 KiB).
  - End: empty body (non-empty => invalid frame).
- Download stream sequence (server): Begin(mime,size,encoding,modifiedAt,revision) -> N Chunks -> End. After the last chunk server re-stats and compares revision; changed => throws `File changed during transfer` (same message if a read returns 0 bytes early).
- Client receive (`dc:7053`): Begin stores state per requestId (ignored unless a `pendingBinaryFileReads` entry exists), Chunk appends (dropped if `size > maxBytes`), End verifies `received === size` else rejects `File transfer incomplete: expected X bytes, received Y.`; kind derived by `binaryFileKind(mime, encoding)` (image/* => image; utf-8 or text/* or application/json => text; else binary).
- Same frames are used client->server for uploads (below). Inbound frames reach `session.ts:3281` -> `wfs.handleFileTransferFrame`.

## Entry mutations: create / rename / duplicate / delete (`fs.entry.*`)
- Requests (msgs:2895-2925, all `{cwd, requestId}` plus): create `{type:"fs.entry.create.request", parentPath, name, kind:"file"|"directory"}`; rename `{type:"fs.entry.rename.request", path, name}`; duplicate `{type:"fs.entry.duplicate.request", path}`; delete `{type:"fs.entry.delete.request", path}`.
- Responses (msgs:6211-6256) `payload`: create `{cwd,parentPath,path|null,success,error|null,requestId}`; rename `{cwd,path,renamedPath|null,success,error,requestId}`; duplicate `{cwd,path,duplicatedPath|null,success,error,requestId}`; delete `{cwd,path,success,error,requestId}`.
- Handlers `wfs.handleFileEntry{Create,Rename,Duplicate,Delete}Request` (wfs:173-245), session.ts:3142-3148; logic in svc `createExplorerEntry`, `renameExplorerEntry`, `duplicateExplorerEntry`, `deleteExplorerEntry`.
  - create: parent must be a directory (`Parent path is not a directory`); file made with `open(target,"wx",0o644)`, folder with `mkdir` (non-recursive); EEXIST => `"<name>" already exists`.
  - rename: target name must not exist unless it is a case-only rename of the same inode (`isCaseOnlyRename`, handles case-insensitive FS); if inside a git work tree and the path is tracked (`git ls-files -z -- :(literal)<path>`, `GIT_LITERAL_PATHSPECS` unset) uses `git mv -- src dst` (preserves rename in index), else `fs.rename`. Missing => `File or folder no longer exists`.
  - duplicate: new name `<base> copy<ext>`, then `<base> copy 2<ext>` ... (first free; dirs have no extension); `fs.cp(recursive for dirs, errorOnExist, force:false, preserveTimestamps, verbatimSymlinks)`.
  - delete: `fs.rm(requestedPath, {recursive: isDirectory, force:false})` (no trash).
- UI pushes errors as toasts (`workspace.fileExplorer.errors.{create,rename,duplicate,delete}Failed`).
- No push event: the app re-lists the parent directory itself. Changes made by agents/outside are only seen on refresh, and for open files via file subscriptions (below).

5. Native filename sanitizing `[\\/:*?"<>|]+ -> _`, empty => `download`.
6. Connections: explorer tree, git diff pane, Host connection types.

## File upload (`file.upload.request`, composer attachments only as a connection)
- Client: `dc.uploadFile` (`dc:5352`) `{fileName,mimeType,bytes,modifiedAt?,requestId?,chunkSize? (default 128*1024)}`: sends JSON `file.upload.request {fileName(min1),mimeType(min1),size:int>=0,modifiedAt,requestId}` with `skipQueue`, then frames FileBegin(mime,size,encoding:"binary",modifiedAt,fileName) -> FileChunk* (a `setTimeout(0)` yield before each chunk; aborts with `DaemonConnectionError("Connection changed during file upload")` if the transport changes) -> FileEnd. Frames race against the response promise (early error response stops sending).
- Response `file.upload.response {requestId, file: UploadedFileAttachment|null, error|null}` (msgs:6305); `UploadedFileAttachment = {type:"uploaded_file", id, fileName, mimeType, size:int>=0, path}` (msgs:1207) is also an `AgentAttachment` union member (msgs:1222), so the composer sends it inside `create_agent`/`send_agent_message` `attachments`.
- Server: `wfs.handleFileUploadRequest` (wfs:378) -> `FileUploadStore` (`server/src/server/file-upload/index.ts`). `beginUpload` registers per (source connection, requestId) with a 10 min stale timeout (`defaultStaleUploadTimeoutMs`, refreshed on each frame; `unref`'d). A repeated requestId cancels the previous upload. Storage: `<paseoHome>/uploads/upload_<uuid>/<sanitizedName>`. Begin creates dir + empty file; each chunk `appendFile`; chunk before Begin => `Upload chunks arrived before file begin.`; running total `> size` => `Upload exceeded declared size: expected X, received Y.`; End with total != size => `Upload size mismatch: expected X, received Y.` and the dir is removed; any error removes the dir and answers with `error`. Cancel (connection ownership release or stale timeout) removes the dir if not completed. Completed uploads are NOT deleted by this store (no TTL cleanup found: looked in file-upload/index.ts).
- `sanitizeFileName`: `basename`, replace `[\p{Cc}\\/:*?"<>|]` with `_`, trim; empty/`.`/`..` => `upload`; truncated to 255 bytes keeping the extension (`fitFileNameLength`). No size cap other than the 100 MiB WebSocket message limit per frame and app-side limits (`app/attachments/upload-limit.ts`, composer; owned by the composer slice).
- Frame ownership: operations are bound to the sending connection (`ownership.operation(...)`, `SessionDelivery`) so frames from another socket are ignored (`pending.get(source)`).

## Live file subscription (`fs.file.subscribe` / `fs.file.update` / `fs.file.unsubscribe`)
- Protocol: `fs.file.subscribe.request {cwd,path,subscriptionId?,requestId}` (msgs:2869); response `fs.file.subscribe.response {subscriptionId, initial: FileVersion, requestId}` (msgs:6175); push `fs.file.update {subscriptionId, version: FileVersion}` (msgs:6258); `fs.file.unsubscribe.request {subscriptionId,requestId}` -> `fs.file.unsubscribe.response {subscriptionId,requestId}`.
- `FileVersion` (msgs:2843), discriminated by `status`: `ready {cwd,path,size,modifiedAt,revision?,kind?:"text"|"image"|"binary",mimeType?}` | `missing {cwd,path}` | `error {cwd,path,error}`. `kind`/`mimeType` come from extension plus first-8-KiB sniff so the client can pick a panel before reading.
- Handler `wfs.handleFileSubscribeRequest` (wfs:82) uses `SessionDelivery.begin("files", subscriptionId, release, "file:"+id)` (owned subscriptions; released on unsubscribe or connection close). Updates that arrive before the subscribe response is sent are held in `pending` and flushed once after it. Failure => subscribe response with `initial:{status:"error",...}` and the owner released.
- Server watcher `FileObserver` in `server/src/server/file-explorer/observer.ts` (singleton `workspaceFileObserver`; NOT the same as `server/src/server/file-observer/`). Per resolved file path one `ObservedFile` shared by all listeners: `fs.watch(dirname)` (non-recursive) filtered to the basename (or null filename), debounce `50 ms`, then re-stat (`getExplorerFileVersion`) and emit only if the fingerprint changed (`status` or `status:revision|size:modifiedAt`). On watcher error or creation failure falls back to `setInterval(5_000)` polling. Listener identity (`cwd`,`path` as the subscriber named them) is substituted into every update so aliases (different cwd strings for the same file) get their own spelling. Last unsubscribe stops watcher/timers.
- Client: `dc.observeFile` / `dc.subscribeFile(input,onUpdate)` (`dc:5253-5286`) built on `observe(...)` OwnedSubscription: after a reconnect the new snapshot is delivered via `onUpdate(snapshot.initial)` to repair missed changes.
- Consumers: file handle (`app/file-panels/file/handle.ts`) described below.

## FileHandle / file session (the editor-facing file API)
Files: `app/file-panels/file/handle.ts` (413 lines), `daemon-session.ts`, `hook.ts`; plugin-facing type `PluginFile` in `packages/plugin/src/client/file.ts`.
- `FileSession` (host abstraction): `observe(target, cb)`, `read(target)`, `write({target, content, expectedModifiedAt, expectedRevision?})`, `createUrl({target, bytes, mimeType})`. Daemon implementation `createDaemonFileSession(client, {workspaceFileEditing, fileByteWrites})`:
  - `observe`: if `!workspaceFileEditing` (daemon < v0.2.0) reads the file once and uses it as the stat (no live updates). Else `client.subscribeFile` and classifies each `FileVersion` into `FileObservation` (adds `kind`/`mimeType`; if the version lacks them (`COMPAT(fileVersionKind)` pre-0.13) one `readFile` supplies them and later versions reuse it, else error `The file has no kind.`).
  - `read` = `client.readFile(cwd, path)` (binary frames when available; no `maxBytes`, default timeout).
  - `write`: string content => `client.writeFile({cwd,path,content,expectedModifiedAt,expectedRevision})`; bytes require `fileByteWrites` (else error `Update the host to write binary files.`) and are base64 encoded in 0x8000-byte slices with `contentEncoding:"base64"`; no `workspaceFileEditing` => `Update the host to edit files.`
  - `createUrl`: persists bytes as a preview attachment (`persistAttachmentFromBytes`, id from `createPreviewAttachmentId({mimeType,path,contentLength,contentKey:Date.now()})`) and returns `resolveAttachmentPreviewUrl`; `release()` releases it. On web this is a `blob:` URL, on native a file URI.
- `FileHandle` semantics (class doc in handle.ts:71-83): keeps `base` = the version last read or written; every write sends `expectedModifiedAt`/`expectedRevision` of `base`. Versions seen (`seen` set keyed by `revision ?? size:modifiedAt`) do not notify watchers, so the handle's own reads and writes are not echoed. Reads wait for queued writes (`this.writes`). Writes run serially and wait while `holdWrites` holds are active.
  - `performWrite`: expected = `base` (or with `force`, the latest `stat ?? base`). `written` -> adopt version. `error` -> `Error(result.error)`. `conflict` with `version.status==="missing"` -> `PluginFileDeletedError` ("The file was deleted."); other conflict -> `PluginFileConflictError` ("The file changed on disk."). With `force` the first conflict whose disk version is `ready` is retried once against that disk version (overwrite). No base => `PluginFileConflictError`.
  - Deletion is only reported after a confirming read: an observed `missing` triggers `confirmDeletion` (read; if the read succeeds the new contents count as a change; if it fails and the latest observation is still `missing` -> emit `{type:"deleted"}`), so a program that deletes and rewrites a file does not look like a deletion.
  - `readText` strips nothing but remembers a UTF-8 BOM (`EF BB BF`) and `writeText` writes it back; decoding via `utils/decode-utf8`.
  - `url()` caches one URL per version key and releases the previous URL when a newer version resolves or on dispose.
  - `file` (`PluginFile`) exposes `{path (absolute), name, extension (lowercase, no dot), size, modifiedAt, mimeType, readText, readBytes, url, writeText(text,{force?}), writeBytes, watch(listener)}`; events `{type:"changed"}|{type:"deleted"}`; errors `PluginFileConflictError`, `PluginFileDeletedError`. React helpers `useFileText`, `useFileBytes`, `useFileUrl` re-read on `changed`, and turn `deleted` into an error state.

## Server directory observer (`server/src/server/file-observer/`, recursive dir watching)
Not user-facing and not used by file tabs; it feeds git working-tree refresh for workspaces (`workspace-git-service.ts:70,640`, `createFileObserver()`; another slice owns git).
- API (`file-observer/index.ts`): `FileObserver.subscribe(directory, callback(error|null, events[]), {ignore?: string[]}) -> {updateIgnore(paths), unsubscribe()}`, `getDiagnostics()`, `close()`. `FileChange = {path, type:"create"|"update"|"delete"}`. Root must exist and be a directory (`File observation requires a directory: <root>`). After `close()`, subscribe throws `File observer is closed`.
- Backends: Linux uses a non-recursive `fs.watch` per directory (`linux.ts`, `MAX_WATCHED_DIRECTORIES = 5_000`, `RECONCILIATION_DELAY_MS = 50`, `MAX_CONCURRENT_CLASSIFICATIONS = 32`, `MAX_QUEUED_CLASSIFICATIONS = 16_384`; overflow fails the observation loudly (`directoryLimitFailureCount`) and workspace-git falls back to bounded polling). macOS/Windows use `fs.watch(root,{recursive:true})` (`native-recursive.ts`, `MAX_TRACKED_ENTRIES = 250_000`, classification queue 2_048, audits: quiet 500 ms/max dirty 5 s; optional audit 8 s/8 s; full audit quiet 30 s, min interval 30 s, max dirty 5 min).
- Event shaping (`internal/observation.ts`): events batched per `EVENT_BATCH_DELAY_MS = 10`, merged per path (`create`+`delete` -> `update`; `delete`+`create` -> `update`; create stays create; later wins otherwise); ignored roots (`normalizeIgnoredRoots`: resolved, inside root, collapsed to parents) filtered; failure sets status `failed`, calls `callback(error, [])`, closes the backend. Path comparison is case-insensitive on win32 (`internal/paths.ts`).
- Distinct from `file-explorer/observer.ts` (single-file stat watcher for `fs.file.subscribe`, above).

## Directory sync (`server/src/server/directory-sync/`, sequenced agent/workspace/project directory)
Not filesystem related: a cursor-based latest-state replica protocol for the app's agent, workspace and project lists (gated by `server_info.features.directorySync`).
- `DirectorySyncService` (`directory-sync/index.ts`, one per daemon, `generation = randomUUID()`; background variant `"<generation>:background"`) owns three `VersionedCollection`s (projects by `projectId`, workspaces by `id`, agents by `agent.id`; `directory-sync/internal/versioned-collection.ts`): monotonically increasing `seq` per change (fingerprint = `JSON.stringify(value)`; unchanged values do not advance), tombstones for removals (`maxTombstones` 5_000; trimming advances `expiredThroughSeq`), `readSnapshot(reason)`, `readAfter(afterSeq)` (cursor expired when `afterSeq < expiredThroughSeq || afterSeq > headSeq`).
- Protocol: request field `sync?: {generation?: string, afterSeq?: int>=0}` on `fetch_agents_request` (msgs:1317), `fetch_workspaces_request` (msgs:1363), `project.list.request` (msgs:1369). Response `sync: {generation, headSeq, mode:"snapshot"|"changes", reason?:"no_cursor"|"generation_changed"|"cursor_expired"|"changes_too_large", removals:[{id,seq}]}` and each entry gets `syncSeq`. Mode `changes` returns entries with `seq > afterSeq` plus removals; otherwise a full snapshot with reason. ## Private files and atomic file writes (server persistence helpers)
- `server/src/server/atomic-file.ts`: `writeFileAtomic(path, data(utf8), runtime?)`: mkdir -p parent, write to `.<basename>.<pid>.<Date.now()>.<uuid>.tmp` in the same dir, `rename` over the target, remove temp on failure. On Windows only, `rename` failing with EPERM/EACCES/EBUSY is retried with backoff (start 10 ms, doubling, cap 100 ms) inside a 1 s total budget (scanners/readers briefly lock files). `writeJsonFileAtomic(path, value)` = `JSON.stringify(value,null,2)`. Does not fsync and does not follow symlinks for the destination (rename replaces a link).
- `server/src/server/private-files.ts`: `PRIVATE_DIRECTORY_MODE = 0o700`, `PRIVATE_FILE_MODE = 0o600`; `ensurePrivateDirectory(dir)` (mkdir -p mode 0700 + chmod), `ensurePrivateFile(file)`, async variant, `writePrivateFileAtomic(Sync)(path, data)`: parent dir 0700, resolves the destination through `realpath` so a symlinked file is written through (rename would replace the link), temp `.<basename>.<pid>.<uuid>` written 0600, rename, chmod 0600; chmod is a no-op on win32 and failures are swallowed. Users (grep): daemon keypair, pid lock, persisted config, server id, agent storage, workspace registry, schedules, push tokens, plugin sources, terminal worker records, etc. (`server/src/server/{daemon-keypair,pid-lock,persisted-config,server-id,workspace-registry}.ts`, `agent/agent-storage.ts`, `schedule/store.ts`, `push/token-store.ts`, `plugins/managed-source.ts`, `terminal/*`).
- Contrast: workspace file writes (`fs.file.write`) use their own temp+revision-check+rename in `svc`, preserve the target's mode, and are NOT these helpers.
