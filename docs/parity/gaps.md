## Permission cards and plan/mode approval

- **Entry/UI:** `A/agent-stream/view.tsx:143-165,1513-1738` renders each agent's pending requests after the timeline, including in an empty chat. `PermissionRequestCard` displays title/description and tool details (200px maximum detail height); kind `plan` uses `PlanCard`, markdown from `metadata.planText` then `input.plan`. Kind `mode` uses the ordinary card, not a separate mode dialog.
- Request contract: `P/agent-types.ts:447-487` defines `AgentPermissionRequest {id,provider,name,kind:tool|plan|question|mode|other,title?,description?,input?,detail?,suggestions?,actions?,metadata?}`. Actions contain `{id,label,behavior:allow|deny,variant?,intent?:implement|implement_resume|dismiss}`.
- Provider actions take precedence. Otherwise buttons are `reject` / `accept`, translated Deny / Accept (Implement for plans). Responses send `{behavior:allow,selectedActionId}` or `{behavior:deny,selectedActionId,message:"Denied by user"}`. Button spinner follows selected action and all actions disable during the mutation. `suggestions` are carried by the protocol but this card does not expose an editor for them.
- **Flow:** `PermissionRequestCard` React Query mutation → `C/daemon-client.ts:6237 respondToPermissionAndWait(agentId,requestId,response,15000)` → `agent_permission_response {agentId,requestId,response}` (`P/messages.ts:2236`) → `S/session.ts:5181 handleAgentPermissionResponse` → `S/agent/permission-response.ts:22 respondToAgentPermission` → `AgentManager.respondToPermission` (`S/agent/agent-manager.ts:3309`) → provider session.
- Allow response may also carry `updatedInput`, `updatedPermissions`; deny may carry `message`, `interrupt`. If provider returns `followUpPrompt`, the helper starts a replacement run (`replaceRunning:true`), important for plan implementation and idle async answers. Codex plan behavior is provider-specific, not just hiding a card.
- **Outcome/errors:** client waits for `agent_permission_resolved.payload` matching BOTH agentId and requestId, bypasses offline queue (`skipQueue:true`), and times out after 15,000ms. This is an answer acknowledgment timeout, not request expiry. Plain `respondToPermission` (`C:5913`) only sends and returns. Modern session replies directly even if sender has no event subscription (`S/session.ts:5195`). Server failure emits `activity_log` error, not a typed negative resolved reply; the waiting card can therefore time out. Ordinary card logs mutation errors; question card additionally displays translated response failure.
- Manager prevents concurrent submissions for one request with `inFlightPermissionResponses`, error `A response to this permission request is already being submitted`. It deletes pending state after success, refreshes/persists/emits, and buffers provider resolution until this completes (`:3316-3348`). A second client can see an already-resolved/stale-request provider error.
- **Platforms:** same contract and cards on native/web/desktop; compact layout changes action arrangement. CLI permission-answer commands exist under `packages/cli/src/commands/permit` (documented below); client API is the common answer surface.
- **Connections:** provider runtime/mode, timeline plan rendering, agent state, attention, parent completion subscriptions, voice policy; approval is distinct from host/device authorization in area 5.

## Agent question forms and answer encoding

- **Entry/UI:** `A/components/question-form-card.tsx:365-675`, selected by `request.kind === "question"` in `A/agent-stream/view.tsx:1650`. Numbered question navigation shows answered/current items; markdown question, radio or checkbox options, description/preview, custom text, Next/Submit and Dismiss. All selections start empty (the first option is not auto-submitted or preselected here).
- **Input contract:** `A/components/question-form-card-core.ts:30-77` requires nonempty `questions[]`, each `{question:string,header:string,options:[{label,description?,preview?}],multiSelect?,allowOther?|isOther?,allowEmpty?,placeholder?,dismissLabel?}`. Invalid input returns null and the card renders nothing (`question-form-card.tsx:569`). This parser has no fixed maximum question/option count or expiry timer.
- Questions without options always get a text input. Otherwise free text requires `allowOther` or `isOther`. `allowEmpty` permits empty text only when text input is available. Primary action is disabled until current question (Next) / all questions (Submit) are answered; single-select auto-advances. Selecting an option clears single-select custom text; typing clears that option. Multi-select retains both.
- **Flow:** local component `selections`, `otherTexts`, `activeQuestionIndex` → `buildQuestionFormAnswers` (`core.ts:124`) → ordinary permission response `{behavior:"allow",updatedInput:{...request.input,answers:Record<header,string>}}` → common answer RPC from previous feature. Multi-select labels join with `", "`; custom answer replaces single-select labels or appends to multi-select. Header is the map key (not question id).
- Dismiss normally sends `{behavior:"deny",message:"Dismissed by user"}`. If every question is free text with `allowEmpty` and zero options, dismiss instead sends allow with encoded answers, including empty strings (`core.ts:161`, card `:470`). Custom dismissLabel overrides translated Dismiss.
- **Provider mapping:** Claude `S/agent/providers/claude/agent.ts:218-310,2903` maps header-keyed answers to full question text expected by `AskUserQuestion`, merges original input, rejects invalid/empty answers with `ClaudeQuestionAnswerRequiredError` (`code:question_answer_required`). Codex blocking questions normalize provider ids/headers and map back to `{[id]:{answers:string[]}}` (`codex-app-server-agent.ts:1233,1354,4748`); denial returns empty answers and failed/canceled tool card. OpenCode/Pi/OMP question mappings are their provider adapters (provider section in B).
- Error prop `responseError` is shown inline, selections remain available for retry; in-flight state disables controls and displays Submit/Dismiss spinner. Input text and selections live only in React component state, not the draft store or daemon config.
- **Platforms:** shared native/web UI with compact action layout; accessibility radiogroup for single-select and checkboxes for multi-select (`card.tsx:544`).
- **Connections:** shared permission channel, provider-specific answer validation, timeline tool result, composer human response and attention; do not implement questions as unrelated messages without request identity.

## Nonblocking Codex questions and durable pending requests

- **User behavior:** `request_user_input_async` can leave a question card while Codex continues its turn. It uses the same QuestionFormCard as blocking questions, so pending request must survive a completed provider message (`S/agent/providers/codex/async-questions.ts:23-111`).
- `CodexAsyncQuestions.receive` accepts `{type:"agentMessage",id,delivery:"async",questions:[{title,options?:string[]}]}`, deduplicates by `permission-${item.id}`, emits question request with headers `Question 1`, etc., `isOther:true`. The corresponding timeline entry is a completed tool call, independent of pending answer.
- **Answer path:** common permission RPC → Codex `respondToPermission` (`codex-app-server-agent.ts:4698`) → `respondToAsyncQuestion` (`:4797`). Allow validates every `updatedInput.answers["Question N"]` as nonempty; denial marks dismissed. While a foreground turn exists, answer text `Answers to your questions: ...` is steered into that exact turn; changed turn errors `The active Codex turn changed. Retry sending your answer.` without completing the question. Otherwise returns `followUpPrompt` for the shared helper to start a turn.
- Resolution updates tool timeline and emits permission_resolved. Reanswer rejects `Question is no longer pending`. Retaining history removes orphan pending ids. No intrinsic question deadline found in this class.
- **Storage distinction:** general pending requests live in `ManagedAgent.pendingPermissions:Map` and provider resolver maps, not a standalone SQLite approvals table or serialized pendingPermissions field (`S/agent/agent-storage.ts:46-84`). Snapshot exposes `pendingPermissions` to clients. Resume refreshes them from provider `getPendingPermissions` (`agent-manager.ts:4307`).
- Codex async records are explicitly serialized as provider persistence `metadata.asyncQuestions` (`codex-app-server-agent.ts:3568,4961`), including resolution; AgentStorage persists the handle. Thus these requests can be reconstructed after resume. Ordinary in-flight SDK promises are not made durable merely by persisting an agent record.
- Local replica cache deliberately strips pendingPermissions to `[]` (`A/runtime/replica-cache/index.ts:245,657`): reconnect must take authoritative snapshot/events, not show offline persisted actionable approvals.
- **Platforms/connections:** all clients share request identity; provider persistence, resume, timeline retention, steer vs follow-up turn, and offline cache semantics must remain aligned.

## Permission event fan-out, cancellation and mode policy

- **Flow to every observing client:** provider emits `permission_requested` → manager `onStreamPermissionRequested` (`S/agent/agent-manager.ts:4959`) inserts pending map, refreshes persistence, emits state and first-pending attention callback → each Session's manager subscription (`S/session.ts:2000-2110`) forwards stream and emits `agent_permission_request {payload:{subscriptionId?,agentId,request}}` (`P/messages.ts:5327`). Internal agents are suppressed from session-wide prompts; exact-id stream subscribers may still see them.
- App SessionProvider observes `agent_permission_request`/`agent_permission_resolved` (`A/contexts/session-context.tsx:484,537-571`); request inserts `${agentId}:${request.id}` in host's `pendingPermissions` Map; resolution removes it (fallback scans by ids). Agent snapshot hydration also reconciles pending list (`A/panels/agent-panel.tsx:291-307`). Agent panel filters requests by agent and passes them into AgentStream (`:1417-1451`).
- Resolution is both an observing-client domain event (`emitSubscribedEvent`) and a modern direct outcome to the answering socket. It is not broadcast indiscriminately to unauthenticated/unsubscribed clients: owned event subscriptions/filtering and session authorization apply (`S/session.ts:1719,2085,8850`; see area 5).
- **Cancellation:** manager denies pending requests with `Interrupted` on cancellation / interruption and `Turn failed` on failed turns (`agent-manager.ts:3408,4881,4917,4989`). Claude permission promise listens to SDK abort signal, emits deny `Permission request canceled`, rejects `Permission request aborted` (`claude/agent.ts:5207-5240`); no human-answer timeout is installed there.
- Human typed/spoken prompt path uses `clearPendingPermissions:true` (`S/session.ts:4074`), so a fresh message can supersede what the agent was blocked on rather than leaving an unusable card. Provider permission-clearing steer paths are therefore relevant to send/steer semantics.
- **Mode policy:** provider-specific modes determine whether requests are generated (full mode tables already in `parts/B-providers.md`). UI does not run a separate global approval policy. Mode changes can apply next turn (Codex) and plan approval can explicitly select implement vs implement_resume actions (Claude). `selectedActionId` must be preserved.
- Voice sessions auto-allow only tool requests whose normalized name is the speak tool (`S/voice-permission-policy.ts:5`, `S/session.ts:2042`); question/plan/mode are not blanket-approved in voice mode.
- **Limits/platforms:** no general server TTL or automatic default answer found in manager permission handlers, Claude permission callback, question form, or common response helper; 15s is only the client response wait above. Web/mobile/desktop use the same subscription and snapshot recovery; provider process loss is not equivalent to a user denial unless an adapter resolves it that way.
- **Connections:** owned subscriptions, authorization, timeline vs control events, snapshot recovery, transport reconnect, voice, interrupt, provider mode settings.

## CLI permission listing, allow and deny

- **Entry:** `paseo permit ls`, `permit allow <agent> [req_id] [--all] [--input <json>]`, `permit deny <agent> [req_id] [--all] [--message <msg>] [--interrupt]`, host/JSON options (`packages/cli/src/commands/permit/index.ts:8-39`). These are missing from earlier permission/UI documents.
- List connects target daemon → `client.fetchAgents({filter:{includeArchived:true}})` → each returned agent.pendingPermissions → table AGENT/REQ_ID/TOOL/DESCRIPTION (`permit/ls.ts:18-79`); empty list is a valid result. Full ids remain in JSON, displayed agent prefix 7/request prefix 8.
- Allow/deny first `fetchAgent({agentId:idOrPrefix})`, server resolves identifier; lookup request exact id or FIRST matching startsWith prefix (`allow.ts:152`, `deny.ts:76`), no client ambiguity rejection. Snapshot absence/no pending/missing request return AGENT_NOT_FOUND/NO_PENDING_PERMISSIONS/PERMISSION_NOT_FOUND.
- **Asymmetric default:** allow with omitted req_id targets ALL pending requests, --all retained as explicit alias; deny requires req_id unless --all or MISSING_ARGUMENT. A Rust port must preserve or deliberately revise this visible behavior, not infer symmetry from help text.
- Allow parses --input as JSON before connecting, INVALID_JSON on parse failure, sends allow+updatedInput when truthy. This enables structured question answers via answers map but CLI does not render interactive QuestionFormCard or synthesize per-provider answer text.
- Deny sends behavior deny plus optional message/interrupt. Batch uses Promise.all with `respondToPermissionAndWait` for each request (same 15s default as app). Results print allowed/denied ONLY after domain acknowledgement; failure PERMISSION_RESPONSE_UNCONFIRMED advises permit ls, rather than claiming timeout implies denial.
- Common wire `agent_permission_response` and server/provider flow above; no extra CLI storage or per-shell approval owner. Partial batch completion possible when another promise rejects; client always closes in success/failure cleanup.
- **States/errors/platforms:** structured CLI CommandError wrappers LIST_PERMISSIONS_FAILED/ALLOW_PERMISSION_FAILED/DENY_PERMISSION_FAILED; desktop/server shell surface, remote --host target owns requests. No native mobile CLI assumed.
- **Connections:** snapshots, identifier resolution, question updatedInput validation, provider plan actions, cross-client resolution and stale-request races; server response timeout is not request expiry.

## Hub daemon relationship, grants, reconnect and revocation

## Cross-area connections

- **Approval → provider and timeline:** request kind/actions/selectedActionId and updatedInput/permissions control tool continuation, plan implementation and question result cards; 15s answer confirmation differs from provider-turn deadlines.

- **Attention → workspace/sidebar/notifications:** pending-input bucket, durable unread edge, parent-delegation callback suppression and presence policy are separate inputs. Heartbeats route OS/push notifications without assigning exclusive answer ownership.
- **Profiles → creation and live config:** host shared config plus provider/model/mode/feature discovery materializes into draft or serialized live setting mutations; device preferences remember values, not a live profile binding. Partial provider failures remain observable.
- **Accounts → usage/providers/Hub:** quota source+account association is not provider selection; custom provider env/plugin routing differs from core profiles. Hub CLI credentials and daemon grants have separate ownership and revocation.
- **Skills → onboarding/MCP/composer:** bundled filesystem installation/selection is host-level; provider-native skill commands enter slash autocomplete independently; profile schema has no skill list.
- **Titles/metadata → project/git/workspace:** provisional agent title and manual tab rename differ from generated workspace title/branch; host candidate order, current selection and project style overrides also drive commit/PR generation.
- **Appearance → every presentation surface:** theme tokens/typographic ramp/width/syntax affect chat/editor/diff/terminal/sidebar; plugin contribution identity and host availability govern contributed themes, local settings govern selection.
- **Localization → settings/onboarding/plugins:** bundled synchronous locale backend renders core UI before children; plugin text resolution is separate, locale preference local to client.
- **Onboarding → host hydration/projects/skills/pairing:** startup gate demands directory; step visit tokens contain late async results, project add and orchestration mutations advance only after success; skipped flow does not rollback prior choices.
- **Storage → reconnect/layout/drafts:** validated local envelopes protect hydration; replica row schemas/cursors/budgets paint stale state safely, then authoritative host state replaces it; pending permissions and provider persistence handles are stripped.
- **Performance → timeline/runtime/query:** opt-in native/browser traces, explicit query invalidation, cache coalescing and startup appearance gate reduce work without changing agent/provider lifecycle semantics.
- **Workspace labels → compound registry and sidebar:** retained journal bounds and generation drive catch-up; catalog/workspace rollback uncertainty blocks mutations rather than publishing divergent filter state; full UI/RPC in p1.
- **Subagents → parent/host/layout/lifecycle:** cross-host address joins managed children, provider-native read-only descriptors, parent navigation and archive/detach. Local provider dismissal differs from real child archive; child tab close differs from root close.
- **Hub → authorization/provider/worktree:** CLI login enrolls relationship separately; hub.execute gates owned execution, shared create/archive pipeline enforces ownership and exact MCP preapproval, authority generations retire stale work.
- **Web overlays → keyboard/accessibility/plugins:** top painted layer owns key/focus, IME stays with editing field and plugin popover Escape must not interrupt underlying agent; no server mutation involved.
