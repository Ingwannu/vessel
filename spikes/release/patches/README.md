# Crates copied from crates.io and changed

Each directory here is a crate as published on crates.io, with the
smallest change that makes the app build where upstream's does not. They
are used through `[patch.crates-io]` (this workspace's `Cargo.toml` and
the app's), never edited beyond what this file lists, and each changed
file says so at its top (Apache-2.0, section 4(b)). ADR 0035 named this
way ("a pinned copy Vessel can patch"); this is its first use.

## `gpui-pre-windows` 0.3.10

Upstream: the `gpui-pre` snapshot of Zed's `gpui_windows` (zed@08cbb88),
Apache-2.0 (`LICENSE-APACHE` beside it). The `.crate` it was taken from
had SHA-256
`80670f987b920fba019917b2e222ecf2b377f2a6d77872010c7d284c235837b3`.
Removed from the copy: its `Cargo.lock` (unused for a dependency).

Changed: `build.rs`, and three call sites of Direct Manipulation in
`src/window.rs` and `src/events.rs` (the second change, below).

### 1. `build.rs`: shaders compiled for the target, not the host

- Purpose: build the Windows app on Linux (and so on any CI machine),
  with the shaders compiled at build time as a Windows build compiles
  them.
- Upstream's constraint: the script decides whether to compile the HLSL
  shaders with `#[cfg(target_os = "windows")]` and
  `#[cfg(debug_assertions)]`. In a build script those are the machine
  the script runs on, not the target. Built on Linux for Windows in
  release, it compiled nothing, and the crate's
  `include!(concat!(env!("OUT_DIR"), "/shaders_bytes.rs"))` then failed:

  ```
  error: couldn't read `.../gpui-pre-windows-.../out/shaders_bytes.rs`: No such file or directory (os error 2)
      --> .../gpui-pre-windows-0.3.10/src/directx_renderer.rs:1869:5
  ```

  A debug build does not need them at build time, but compiles them at
  run time from the crate's source path on the build machine, so a debug
  `.exe` draws nothing anywhere else.
- Alternatives:
  1. Build on Windows only (a CI runner). Works, and is what CI does
     (`../ci/`); but then no Windows build can be made between pushes,
     and the owner's feedback loop waits on CI.
  2. Precompiled shader bytes checked in. The bytes would have to be
     regenerated by hand at every GPUI move, and nothing would check
     that they match the source.
  3. A compiler native to Linux. DXC emits DXIL (Direct3D 12) only; the
     renderer is Direct3D 11 and needs DXBC. vkd3d's HLSL compiler is a
     reimplementation whose output can differ from Windows'.
  4. **This change**: ask Cargo for the target (`CARGO_CFG_TARGET_OS`,
     `CARGO_CFG_DEBUG_ASSERTIONS`), and on a host other than Windows take
     the compiler only from `GPUI_FXC_PATH`. Vessel points that at
     `../tools/fxc-wine`, which runs Microsoft's own `fxc.exe` with the
     SDK's `d3dcompiler_47.dll` under wine.
- Why 4: the same compiler and flags as a Windows build, so the same
  bytes; the change is a few lines in one file and does not touch the
  crate's code.
- Cost: wine and the two SDK files on the build machine
  (`../tools/setup-windows-cross.sh` fetches them); this copy moves with
  every GPUI pin (re-copy the new version, re-apply the change, which is
  the diff of `build.rs` against the published one). On a Windows host
  the script behaves as upstream's.

### 2. Direct Manipulation is optional

- Purpose: open the window where Direct Manipulation (the Windows API
  behind a precision touchpad's smooth panning and pinch) cannot start,
  instead of failing it; here, so the Windows build can be run and seen
  drawing under wine on Linux, the only Windows this machine has.
- Upstream's constraint: `WindowsWindowState::new` creates the handler
  with `?`, so any failure ends the window. Wine 9.0 implements the API
  as stubs (its trace prints `fixme:manipulation` for
  `ActivateConfiguration`, `SetViewportOptions`, `SetViewportRect` and
  `Activate`), a later call answers `E_NOTIMPL`, and every window failed:

  ```
  vessel-hello: no window: initializing Direct Manipulation: Not implemented. (0x80004001)
  ```

- Alternatives: run the Windows build only on Windows (no evidence of a
  drawn frame before the owner installs it); a stand-in for the API
  under wine (a COM server of our own, test-only); a test-only feature
  of this copy (then the binary run is not the binary shipped).
- Choice: the handler is an `Option`, created with `.log_err()`; the
  three places that use it skip it when absent. Marked `MODIFIED by
  Vessel` in both files.
- Why: on a Windows where Direct Manipulation works, nothing changes;
  where it does not, the window opens and scrolls by the wheel messages
  it always receives; and the build that runs under wine is the build
  that ships.
- Cost: a second change to carry at every GPUI pin; a Windows where it
  fails now loses touchpad gestures quietly (an error in the log)
  instead of not starting.

To see both changes: unpack the published `.crate` and `diff -ru` it
against `gpui-pre-windows/` (only `Cargo.lock` is missing on this side).
