# Crates copied from crates.io and changed

Each directory here is a crate as published on crates.io, with the
smallest change that makes the app build where upstream's does not. They
are used through `[patch.crates-io]` (this workspace's `Cargo.toml` and
the app's), never edited beyond what this file lists, and each changed
file says so at its top (Apache-2.0, section 4(b)). ADR 0035 named this
way ("a pinned copy Vessel can patch"); this is its first use.

## `gpui-pre-windows` 0.3.10

Upstream: the `gpui-pre` snapshot of Zed's `gpui_windows` (zed@08cbb88),
Apache-2.0 (`LICENSE-APACHE` beside it). The `.crate` it was taken from
had SHA-256
`80670f987b920fba019917b2e222ecf2b377f2a6d77872010c7d284c235837b3`.
Removed from the copy: its `Cargo.lock` (unused for a dependency).

Changed: `build.rs`, and three call sites of Direct Manipulation in
`src/window.rs` and `src/events.rs` (the second change, below); added
`src/environment.rs` and its module and export lines in
`src/gpui_windows.rs` (the sixth).

### 1. `build.rs`: shaders compiled for the target, not the host

- Purpose: build the Windows app on Linux (and so on any CI machine),
  with the shaders compiled at build time as a Windows build compiles
  them.
- Upstream's constraint: the script decides whether to compile the HLSL
  shaders with `#[cfg(target_os = "windows")]` and
  `#[cfg(debug_assertions)]`. In a build script those are the machine
  the script runs on, not the target. Built on Linux for Windows in
  release, it compiled nothing, and the crate's
  `include!(concat!(env!("OUT_DIR"), "/shaders_bytes.rs"))` then failed:

  ```
  error: couldn't read `.../gpui-pre-windows-.../out/shaders_bytes.rs`: No such file or directory (os error 2)
      --> .../gpui-pre-windows-0.3.10/src/directx_renderer.rs:1869:5
  ```

  A debug build does not need them at build time, but compiles them at
  run time from the crate's source path on the build machine, so a debug
  `.exe` draws nothing anywhere else.
- Alternatives:
  1. Build on Windows only (a CI runner). Works, and is what CI does
     (`../ci/`); but then no Windows build can be made between pushes,
     and the owner's feedback loop waits on CI.
  2. Precompiled shader bytes checked in. The bytes would have to be
     regenerated by hand at every GPUI move, and nothing would check
     that they match the source.
  3. A compiler native to Linux. DXC emits DXIL (Direct3D 12) only; the
     renderer is Direct3D 11 and needs DXBC. vkd3d's HLSL compiler is a
     reimplementation whose output can differ from Windows'.
  4. **This change**: ask Cargo for the target (`CARGO_CFG_TARGET_OS`,
     `CARGO_CFG_DEBUG_ASSERTIONS`), and on a host other than Windows take
     the compiler only from `GPUI_FXC_PATH`. Vessel points that at
     `../tools/fxc-wine`, which runs Microsoft's own `fxc.exe` with the
     SDK's `d3dcompiler_47.dll` under wine.
- Why 4: the same compiler and flags as a Windows build, so the same
  bytes; the change is a few lines in one file and does not touch the
  crate's code.
- Cost: wine and the two SDK files on the build machine
  (`../tools/setup-windows-cross.sh` fetches them); this copy moves with
  every GPUI pin (re-copy the new version, re-apply the change, which is
  the diff of `build.rs` against the published one). On a Windows host
  the script behaves as upstream's.

### 2. Direct Manipulation is optional

- Purpose: open the window where Direct Manipulation (the Windows API
  behind a precision touchpad's smooth panning and pinch) cannot start,
  instead of failing it; here, so the Windows build can be run and seen
  drawing under wine on Linux, the only Windows this machine has.
- Upstream's constraint: `WindowsWindowState::new` creates the handler
  with `?`, so any failure ends the window. Wine 9.0 implements the API
  as stubs (its trace prints `fixme:manipulation` for
  `ActivateConfiguration`, `SetViewportOptions`, `SetViewportRect` and
  `Activate`), a later call answers `E_NOTIMPL`, and every window failed:

  ```
  vessel-hello: no window: initializing Direct Manipulation: Not implemented. (0x80004001)
  ```

- Alternatives: run the Windows build only on Windows (no evidence of a
  drawn frame before the owner installs it); a stand-in for the API
  under wine (a COM server of our own, test-only); a test-only feature
  of this copy (then the binary run is not the binary shipped).
- Choice: the handler is an `Option`, created with `.log_err()`; the
  three places that use it skip it when absent. Marked `MODIFIED by
  Vessel` in both files.
- Why: on a Windows where Direct Manipulation works, nothing changes;
  where it does not, the window opens and scrolls by the wheel messages
  it always receives; and the build that runs under wine is the build
  that ships.
- Cost: a second change to carry at every GPUI pin; a Windows where it
  fails now loses touchpad gestures quietly (an error in the log)
  instead of not starting.

### 6. Telling running programs the environment changed

- Purpose: after the app adds its command-line tool's directory to the
  user's `PATH` (`HKEY_CURRENT_USER\Environment`, ADR 0094's packaging,
  track W19b), a terminal the person opens next must find `vessel`.
  Windows starts programs with Explorer's copy of the environment, and
  Explorer rereads it only when told: Windows' own settings broadcast
  `WM_SETTINGCHANGE` with `"Environment"` after an edit.
- Constraint: the broadcast is a Win32 call
  (`SendMessageTimeoutW(HWND_BROADCAST, …)`), so `unsafe`; the app's
  workspace forbids `unsafe_code`, and this crate already holds the
  app's Win32 calls behind safe functions.
- Alternatives:
  1. A small crate of the app's own that allows `unsafe`: a new
     workspace member with its own lint exception, for one call.
  2. Running `setx` or PowerShell to do the write and the broadcast: a
     console process, a quoting surface, and `setx` cuts values at 1024
     characters.
  3. **This change**: `broadcast_environment_changed()` in a file of its
     own, exported from the crate root with
     `ENVIRONMENT_BROADCAST_TIMEOUT` (5 s) and a typed
     `EnvironmentBroadcastError` (`TimedOut`, `Failed(windows::core::Error)`).
     `SMTO_ABORTIFHUNG` skips a hung window, so the call cannot wait on
     it forever; nothing in it panics.
- Why 3: one safe function beside the crate's other Win32 calls, no new
  crate or lint exception, and no change to upstream's own files beyond
  two lines in the crate root.
- Cost: a third change to carry at every GPUI pin (the new file copies
  over; re-add the two lines). The call waits for the windows' answers,
  so the caller runs it off the UI thread.
- Checked: compiled for `x86_64-pc-windows-msvc` with `cargo xwin check`;
  its behaviour on Windows (a new terminal finding the new `PATH`) is
  still to be shown on a Windows machine.

To see the changes: unpack the published `.crate` and `diff -ru` it
against `gpui-pre-windows/` (only `Cargo.lock` is missing on this side).

### 3. One XIM input context per window

- Purpose: Hangul (and any input method with an on/off state) stays on
  in Vessel's window across a switch of windows. Before this, a person
  who turned Hangul on in Vessel, went to another window and came back
  typed Latin letters while the input method's indicator still said
  Hangul (`gksrmf` for 한글): the defect reported as "Hangul does not
  compose on X11" (track G1, 2026-11-13).
- Upstream's constraint: on every `FocusIn` the X11 client's
  `enable_ime` asked the input method for a new input context
  (`create_ic`) and never destroyed the old one nor used XIM's focus
  requests. An input method keeps its on/off state per input context
  (fcitx5's default, `ShareInputState=No`), and a new context starts
  off. Measured in G1's harness (a private Xvfb, fcitx5 5.1.7 with
  Hangul over XIM): on, other window, back, typed `gksrmf` → `gksrmf`.
- Alternatives:
  1. Ask people to share the input state across contexts in their input
     method's settings (fcitx5 `ShareInputState=All`). It is theirs to
     set, not the app's, changes every other program too, and nothing
     tells them to.
  2. Destroy the old context and make a new one each time. The state is
     lost the same way.
  3. **This change**: the XIM handler remembers each window's context
     (made the first time the window has the focus); `FocusIn` focuses
     it again (`XIM_SET_IC_FOCUS`) and `FocusOut` unfocuses it
     (`XIM_UNSET_IC_FOCUS`), which is what XIM's focus requests are for.
- Why 3: the input method sees one context per window for the window's
  life, as with any other X client, so its state is the window's; the
  change is a map and two requests, in the two files that handle XIM.
- A syllable half typed when the window loses the focus: upstream reset
  the context (`XIM_RESET_IC`), which threw it away. Now the context is
  only unfocused and the input method decides. fcitx5 commits it when it
  lets the app draw the composition (`UseOnTheSpot=True`: its log shows
  `XIM commit: 하` right after `XIM_UNSET_IC_FOCUS`, and the field keeps
  하 once); in its default style, where fcitx5 draws the composition in
  its own popup, it drops it, as it does for any XIM program (xterm too):
  the app never had that text, so it cannot keep it. Upstream deleted
  the marked text in the field on `FocusOut` and still does (the
  committed text replaces it).
- Cost: a third change to carry at every GPUI pin (re-copy, re-apply
  the diff of the two files). A window's context is not destroyed when
  the window closes (one small entry in the input method per window
  opened; the app opens few).
- Verified on a debug build with track G1's harness (a private Xvfb, a
  private D-Bus session, fcitx5 5.1.7 with Hangul over XIM, keys by
  xdotool), in both fcitx5 styles; captures are local, not committed:

  | Step | Before (upstream) | After |
  |---|---|---|
  | Hangul on, other window, back, type `gksrmf` | `한글 gksrmf` | `한글 한글` (both styles) |
  | `gk` (하 composing), other window, back, `s` | 하 lost | on-the-spot: 하 kept once, then ㄴ composes; default: 하 dropped by fcitx5 (above) |
  | `gk`, a click in the field, `s` | (Hangul already off) | on-the-spot: 하 kept, then ㄴ; default: composes on to 한 |

- Wayland is not changed: the pinned crate's `zwp_text_input_v3` client
  composes in place (sway nested on Xvfb, fcitx5 over input-method-v2:
  한그 drawn with the syllable underlined, then 한글 committed).

### Optional image activation in the existing text engine

- Purpose: Paseo opens an unlinked assistant markdown image in its image viewer.
  The pinned TextView only handled images already wrapped in hyperlinks.
- Choice: add optional `TextView::on_image_click` and the matching editor-host
  setter, copied through TextViewState into NodeContext. Existing plain-image
  and mixed inline-flow elements share `text/image_activation.rs`; image layout,
  source selection, retained parsing, find highlighting and resource resolution
  are unchanged. A host handler owns image activation, including linked images;
  without one, existing linked-image behavior remains.
- Why: a second renderer or rewriting image markdown into links would change
  source ranges and selection. The callback lets the app use its authorized
  acquisition and shared lightbox while the same image element keeps its atom.
- Changed files: `text/{mod,text_view,state,node,inline_flow,editor_host}.rs` and
  the new private `text/image_activation.rs`. No default URL or file opening is
  added for unlinked images.
- Check: kit `chat_markdown::actions::image_tests` covers plain images, mixed
  inline-flow images and linked images with a host handler, plus absence of a
  handler. These tests passed in Kit run `wp-composer-copy-diagnostic-20261115T141044Z-40aaab5d` (195/0 overall); no visual approval is implied.

### Optional inferred text links without source rewriting

- Purpose: Paseo `components/markdown/source.ts:12-55` recognizes file tokens in
  prose and complete inline code, then `assistant-file-links/parse.ts:598-646`
  classifies the target. A custom Markdown inline atom would remove ordinary
  partial selection from those tokens.
- Choice: a typed `InlineLinkRecognizer` function produces validated UTF-8
  ranges which become existing paragraph link marks. It skips explicit links
  (including reference/inline-HTML groups) and fenced code. Equivalent function
  registrations keep the existing parsed document. No text or source segment is
  rewritten; inferred marks do not generate new link syntax during source copy.
- Provenance: the optional `on_link_activate` callback distinguishes authored
  hrefs from inferred Text/Code, preserving literal percent bytes in filenames.
  Existing `on_link_click` signatures remain compatible and receive the same URL.
- Changed files: private `text/inline_links.rs`, extension configuration, Markdown
  parsing, existing link marks/copy, and existing inline/image activation adapters.
  The native kit tests partial selection across a recognized token, source-to-find
  offsets, authored-link priority, and fenced-code exclusion. They passed in the same exact40aa Kit run; strict and later source checks remain separate.
- Compatibility: the kit calls the same Base TextView directly because the pinned
  Component facade does not forward these optional callbacks. The existing
  `TextViewDefaults::style` accessor is public so kit refinements start from the
  exact Component-installed theme, preserving its colors and table geometry.
  This adds no renderer, state owner, theme adapter, or dependency.
- Recognized marks are made disjoint with the renderer's existing highlight
  sweep before source selection walks them. Otherwise a code/emphasis mark and
  its overlapping inferred link copy the same bytes twice. The highlight sweep
  is extracted generically with its body unchanged; marks without inferred
  links keep the original parser path and original source segments.

- Code-aware copy queries the same parsed selection through
  `TextViewState::selected_code_text()`. Inline code and fenced code use their
  existing marks/blocks; mixed prose and multiple code regions retain Markdown.
  This avoids a second fence scanner disagreeing with the renderer (including
  longer fences containing shorter backtick runs). The kit's window aggregator
  still owns selections across messages. Regression coverage is in
  `chat_markdown::actions::link_tests::code_copy_uses_parsed_inline_and_fenced_regions`.
  `text::trim_code_line_breaks` is the one shared LF/CRLF+ASCII-indentation
  cleanup for this query and the kit's existing code-copy button. It implements
  Paseo `assistant-selection-copy/markup.ts:12-19` and
  `components/highlighted-code-block.tsx:95`: keep leading indentation, interior
  newlines and trailing spaces on a nonempty line; remove only final line breaks
  and indentation after them. No regular-expression dependency is introduced.

### 4. A steady caret while motion is held

- Purpose: a focused text field costs nothing while nothing changes.
  The caret's blink notified the field every 500 ms, and the shell is
  one GPUI view, so each blink redrew the whole window: on 0.0.0.0.14 on
  a software renderer about 31 % of a core at 1280 × 800 and 62 % at
  1920 × 1200, the whole time a person is on the new-session screen
  (the coordinator's measure, 2026-11-14). The owner's word 39 asks
  that nothing animate continuously and that reduced motion, the app's
  Animations setting off and a software renderer give the end state at
  once.
- Upstream's constraint: `BlinkCursor` is private to the crate
  (`pub(crate)`) and reads no setting; every field's state starts it on
  focus and on window activation and restarts it 300 ms after each key.
  The app cannot stop it from outside.
- Alternatives:
  1. The app's own text fields. Months of work (gpui-base's input is
     the editor: selection, IME, undo, wrapping).
  2. Hiding the field's caret and drawing the app's own. The field
     would still be notified every 500 ms, which is the cost.
  3. Caching the composer's view so a blink redraws only it. GPUI still
     presents the whole window each frame, and on a software renderer
     presenting is the cost.
  4. **This change**: `BlinkCursor::blink` reads GPUI's
     `App::reduce_motion` and, when it is set, shows the caret and
     schedules no next blink. The app already sets that one flag for
     every reason motion is held (`spikes/native/app/src/motion.rs`).
- Why 4: one condition in the one function that schedules blinks; no
  new API to carry, and the caret follows the same flag as every other
  motion in the app. When the flag clears, the next focus, key or window
  activation blinks again.
- Cost: a fourth change to carry at every gpui-kit pin (re-copy the new
  version, re-apply the diff of the one file). The crate is 5 MB of
  source in the repository.
- Checked: the kit's test
  `field::form_tests::the_caret_is_steady_while_motion_is_held` (a
  focused composer in an active test window: notified at least three
  times in 3 s with motion, never with motion held). The CPU measures
  before and after are in `docs/plans/backend-m12-effort-slider.md`,
  "Known costs".

Changed: `src/elements/div.rs` (change 5), `src/window.rs` and

### 5. A drag starts at the distance an element names

- Purpose: a press on a row that can be dragged stays a press until the
  pointer has clearly moved. Paseo's web draggable list waits 6 points
  before it picks a row up; GPUI starts every drag after 2, so a
  slightly shaky click on a sidebar row (S2's reordering) dragged it.
- Upstream's constraint: the distance is one private constant,
  `DRAG_THRESHOLD`, read by every element's mouse-move listener in
  `Interactivity::paint_mouse_listeners`; no element can change it.
- Alternatives:
  1. The row tracks its own press and move instead of `on_drag`. A
     second drag model beside GPUI's, with its own drag view and drop
     targets, in each list that wants Paseo's distance.
  2. Changing the constant to 6. Every existing drag (the queue's rows,
     the components library's) would change at once.
  3. **This change**: `Interactivity::drag_threshold` and the fluent
     `StatefulInteractiveElement::drag_threshold` store a distance on
     the element; the mouse-move listener compares with it, or with
     `DRAG_THRESHOLD` when the element names none.
- Why 3: one field, two builders and one comparison; every caller that
  names nothing behaves exactly as upstream. The kit names Paseo's
  distance once (`spikes/native/kit/src/drag.rs`, `LIST_DRAG_DISTANCE`).
- Cost: the GPUI core is now a copy to carry at every GPUI pin (re-copy
  the new version, re-apply the diff of `div.rs`), 8 MB of source in the
  repository, and every build target compiles GPUI from this path once.
- Checked: the kit's tests `drag::tests::a_list_row_waits_for_paseos_six_points`
  (5 points: no drag; 7: a drag) and
  `drag::tests::an_element_naming_no_distance_keeps_gpuis_two` (1.5: no
  drag; 3: a drag), through real mouse events in a test window.

### 8. A user zoom per window

- Purpose: the app zooms its whole content as Paseo's desktop app does
  (Ctrl+= / Ctrl+- / Ctrl+0): everything larger and still sharp, less of
  it in the window, and a click landing on what is drawn under it.
- Upstream's constraint: a window's scale is the platform's (the
  display's DPI), read in `Window::bounds_changed`; the one call that
  changes it, `Window::set_scale_factor`, exists for tests only. `rem_size`
  scales only what is sized in rems, and the kit sizes in points.
- Alternatives:
  1. Multiply every size in the kit and the app by a factor. Every token,
     literal size and size test would carry it, and GPUI's own elements
     (scroll bars, the input base) would not follow.
  2. Size everything in rems. A rewrite, with the same gap in GPUI's own
     elements.
  3. **This change**: `Window::set_zoom` and `Window::zoom` keep a
     multiplier on top of the platform's scale. `scale_factor` is the
     platform's times it and `viewport_size` the content size divided by
     it, so layout, paint and hit-testing run in the zoomed space. Events
     from the platform (the window's input callback) arrive with their
     positions and pixel scroll distances divided by it; GPUI's own
     synthesized events are in that space already and are left alone.
     Positions the platform needs leave multiplied by it: the IME's caret
     and selection rectangles and its point lookups
     (`PlatformInputHandler`), the window menu's position, the client
     decorations' inset and the macOS traffic lights. The visual viewport
     and the platform's insets come in divided by it.
- Why 3: one field and one conversion at each crossing between GPUI and
  the platform; text and images rasterize at the zoomed scale, so they
  stay sharp, and nothing in the kit or the app changes its sizes. At zoom
  1 every conversion is skipped or exact, so a window nobody zooms
  behaves as upstream.
- Kept in the platform's space: what is about the window on the screen
  (`bounds`, `window_bounds`, `resize`), so saved window sizes do not
  change with the zoom. `set_zoom` keeps the zoom between
  `Window::MIN_ZOOM` (0.25) and `Window::MAX_ZOOM` (5) and ignores a value
  that is not a finite number; it runs the bounds observers, as a resize
  does.
- Cost: `window.rs` and `platform.rs` join `div.rs` in the diff to
  re-apply at each GPUI pin; a new crossing between GPUI and the platform
  in a later version needs the same conversion.
- Checked: the kit's tests in `spikes/native/kit/src/zoom/tests.rs`,
  through the test window's platform callbacks: at zoom 1.25 a window of
  1000 by 800 points lays out in 800 by 640 and paints at scale 2.5 on a
  display of scale 2, its size on the screen unchanged; a platform resize
  keeps the zoom; a press at 150 platform points lands on a 100-point
  target at zoom 2 and misses it unzoomed; the zoom stays within its
  bounds and ignores a non-number. The IME's rectangles and the window
  menu reach the platform only in a real session and are not checked yet:
  an IME's candidate window and the window menu at a zoom other than 1 are
  still to be looked at in the app on Linux.
